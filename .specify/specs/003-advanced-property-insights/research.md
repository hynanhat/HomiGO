# Research: Advanced Property Insights

## Decision 1: In-app polling notifications

**Decision**: Persist notifications in MySQL and refresh the unread count/list through TanStack Query every 30 seconds, plus immediate query invalidation after read actions.

**Rationale**: It meets the 60-second freshness target, works with the existing stateless REST/JWT architecture and requires no message broker or persistent connection for the current project scale.

**Alternatives considered**:

- WebSocket or server-sent events: stronger real-time behavior but adds connection lifecycle, authorization and deployment complexity that is not required by the specification.
- Email or push notifications: requires third-party delivery configuration and user consent/preferences, explicitly outside the first release.

## Decision 2: Transactional workflow notification creation

**Decision**: Create notifications from the same service transaction that completes listing submission, approval, rejection or expiration.

**Rationale**: The business result and its notification either persist together or both roll back. Existing status preconditions prevent duplicate approval/rejection notifications.

**Alternatives considered**:

- Asynchronous application events: useful at larger scale but can lose atomicity without an outbox and offers little benefit for small local writes.
- Controller-driven creation: violates the project's business-layer rule and risks missed notifications from scheduled transitions.

## Decision 3: Unique daily views with HMAC pseudonyms

**Decision**: Store one row per listing, business date and HMAC-SHA-256 viewer pseudonym. Authenticated users use their immutable user ID as the HMAC input; anonymous visitors use a validated random UUID generated by the browser. The key comes from an environment variable, falling back to the existing JWT secret configuration.

**Rationale**: A unique database constraint makes repeated page loads idempotent, daily rows directly support charts, and the stored viewer value cannot be used without the server secret to recover an account or browser identifier.

**Alternatives considered**:

- Incrementing a counter on every detail request: inflates values on reload, prefetch and retry and cannot produce unique daily statistics.
- Raw IP address or browser fingerprint: creates unnecessary privacy risk and unreliable identity.
- Storing raw browser UUID: operationally simple but exposes a stable tracking identifier if the database is inspected.

## Decision 4: Explicit view-recording action

**Decision**: The public listing page sends one explicit idempotent recording request after a successful detail load instead of counting the detail GET itself.

**Rationale**: Read caching, prefetching and automated requests do not automatically become views. A dedicated action has a clear validation contract and remains safe to retry.

**Alternatives considered**:

- Count inside the listing detail query: couples a read to a write and makes retries/prefetch behavior surprising.
- Count only in the browser: cannot produce trustworthy shared statistics.

## Decision 5: Explainable deterministic recommendations

**Decision**: Select a bounded set of active, unexpired candidates sharing at least one meaningful signal, then rank in the service with fixed weights for category, transaction type, district/province, project and normalized price/area proximity. Newer publication time and ID provide deterministic tie-breaking.

**Rationale**: The algorithm is explainable in a graduation defense, testable with fixtures, uses the project's existing data and avoids new infrastructure. A bounded candidate set prevents loading the full listing table.

**Alternatives considered**:

- Collaborative filtering: needs substantial interaction history and cold-start handling not currently available.
- External AI or vector database: adds cost, network dependency and opaque scoring without enough source data.
- Purely random/latest listings: simple but does not satisfy similarity requirements.

## Decision 6: No chart dependency

**Decision**: Render the 7–90 day series as an accessible CSS bar chart with a tabular/text fallback in the seller detail page.

**Rationale**: The dataset is small and simple; native layout keeps the bundle lean and allows precise responsive and accessibility behavior.

**Alternatives considered**:

- Add a chart library: unnecessary dependency and bundle cost for one compact series.
- Show totals only: does not meet the daily trend requirement.

## Decision 7: Database lifecycle and deletion behavior

**Decision**: Notification references use `ON DELETE SET NULL` so message history remains readable; listing view rows use `ON DELETE CASCADE` because statistics have no value without the listing.

**Rationale**: This matches the edge case for deleted notification targets while keeping analytics storage self-cleaning.

**Alternatives considered**:

- Cascade-delete notifications: removes useful audit/history from the user's inbox.
- Retain orphan view rows: consumes storage and cannot be queried meaningfully.
